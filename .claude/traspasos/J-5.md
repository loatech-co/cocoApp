# J-5 — cerrar el INSERT de `coco_app` sobre `users` (borrado: nada)

**Hecho**

- Migración `20261010003334_guard_users_insert`: trigger `BEFORE INSERT OR UPDATE`
  en `users` → `app_private.guard_users_access()` (no definer, `search_path`
  vacío, sin EXECUTE para PUBLIC). Solo actúa con `current_user = 'coco_app'`:
  INSERT de `user`/`pending` sin aprobar, o del primer admin activo mientras no
  haya NINGÚN admin (lock consultivo); UPDATE nunca cambia rol, estado ni
  aprobación. Lo demás: 42501. La API no cambia: funciona con y sin ella.
- e2e (`row-level-security.e2e-spec.ts`): cuatro formas rechazadas, alta normal,
  primer admin, segundo admin rechazado, admin suspendido cierra el bootstrap,
  autopromoción por SQL rechazada. `migrate diff` vacío.
- ADR 0027; runbook, «Guard on `users` inserts (J-5)»: aplicar, comprobar y
  deshacer; `db.dump` incluye `app_private`.
- El respaldo sin `app_private` se renombró con el sufijo `-incompleto`
  (`coco-datos/respaldos/`); el siguiente sí lo trae.

**J-5b (rama `fix/bootstrap-admin-orphan`)**

- El alta pregunta `hasAnyAdmin()` antes de Supabase: con un admin ya
  existente, `BOOTSTRAP_ADMIN_EMAIL` entra como `user`/`pending`.
- Si el perfil falla tras crear la credencial, se borra con
  `SupabaseAuthService.deleteUser` y el alta falla. Con su e2e.
